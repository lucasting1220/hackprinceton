## Summary

- **Current release.** iOS 27.2.1 is current [S1]. iOS 27 changes nothing relevant in Keychain sharing, the NSE API, local-network privacy for iOS apps, ATS for apps, VisionKit or AVFoundation QR scanning (from a scan of the iOS 27 release notes) [S2]. These changes do touch Debbie, and all need the iOS 27 SDK: HealthKit's "limited history" authorization [S2][S33]; Xcode 27's `@State` macro, which stops re-running initial values and **breaks some code that compiles today** [S2]; the `@Entry` macro's new **warning on default class instances and closures** [S2]; MetricKit's `MemoryExceptionDiagnostic` for extensions killed over their memory limit [S2]. R4 keeps today's code compiling on Xcode 27.
- **Project structure.** An Xcode project generated by **XcodeGen 2.46.0**, pinned by its GitHub release zip and SHA-256 (Homebrew can't pin a version) [S45][S46][S47][S49], from `project.yml`, plus **one local Swift package** with about ten library targets. SwiftPM can't describe an app or an app extension [S58]. Neither SwiftPM nor XcodeGen can link a dependency only in one configuration [S58][S46], so Debug-only code compiles to nothing in Release, and a check of the unstripped Release build and the shipped binary's strings proves it (R6).
- **Minimum iOS 26.0** (lead decision X18; note 02). Package `platforms: [.iOS(.v26)]`. Every iPhone that runs iOS 26 (iPhone 11 and SE 2nd gen onward) has an A13 or later [S77][S78].
- **Concurrency.** Every module adopts Apple's Approachable Concurrency features, which Apple recommends for all projects [S8]. UI modules add MainActor default isolation. Core, Crypto, SecureStore, Networking and the NSE stay `nonisolated`, and heavy work is marked `@concurrent`. The NSE **must** stay `nonisolated`: under MainActor default isolation it fails to compile with three errors (verified locally) [S62].
- **Keychain.** One `keychain-access-groups` group, `$(AppIdentifierPrefix)<bundle id>.shared`, on the app and the NSE, with `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly` [S11][S12][S51]. No App Group is needed tonight. Keychain tests must run hosted inside the app, because logic tests run in `xctest` without entitlements [S15].
- **Notification Service Extension.** It has about 30 s [S17] and **24 MB in total, including linked code** [S19]. So it links only Core, Crypto and SecureStore and never touches the network. `simctl push` never runs an NSE [S25]. Real sandbox pushes to the Simulator do [S26], but sending any APNs push needs the team's APNs auth key or certificate [S20][S72], which Layer 1 keeps on the relay side [S64]. So tonight the real NSE class is tested app-hosted with a synthesized request (R14).
- **Push contract.** Relay-written notices are only "hub offline" (`active`) and "back online" (`passive`), with `mutable-content: 1` and a `last_contact` Unix time. "Monitoring degraded" is an encrypted hub message. Headers travel as SNS message attributes (R12) [S64][S66][S67].
- **HealthKit.** Use `HKAnchoredObjectQueryDescriptor` with a persisted anchor, and a first-run date predicate, because a nil anchor reads *all* history [S30]. While the phone is locked the store is encrypted and reads fail (`errorDatabaseInaccessible`) [S29][S52]. Background delivery needs an entitlement and a device, and wakes the app at most once per period whenever samples are saved. Apple doesn't document a heart-rate frequency on iOS [S31][S32]. It is LATER on cut-order grounds (R17).
- **Local network and Bonjour.** There's no API to request or check permission. The first operation may be denied while the alert is still showing, so pairing waits and retries [S35]. The app browses Layer 1's `_debbie._tcp` and keeps only services whose TXT record carries its hub-key prefix [S64]. It resolves a match to an IPv4 address and confirms it with an encrypted request before storing it. Every wait has a deadline (denied, no Wi-Fi, wrong network, found) (R25). The Simulator has no local-network privacy at all [S35].
- **ATS.** Since iOS 17, ATS blocks IP addresses by default. `NSAllowsLocalNetworking` re-allows *every* IP address, `.local` names and unqualified names [S38], public addresses included. So ATS can't enforce the brief's "plain HTTP only to local-network addresses". A code guard (R26) allows `http://` only to an IPv4 address on the phone's own Wi-Fi or Ethernet subnet, which is Apple's definition of a local network address [S35]. It allows `127.0.0.1` only in Debug. The Layer 1 doc's ATS claim is confirmed [S64].
- **QR scanning.** Use VisionKit `DataScannerViewController` (iOS 16, A12 Bionic or later) with system guidance and highlighting off. Debbie's own viewfinder snaps onto the code, so high-frame-rate tracking stays on [S42][S43][S53]. One scanner serves both the pairing code and the "Add this laptop" code, with a clear wrong-code state (R21). No AVFoundation fallback is needed: every iOS 26 iPhone exceeds the A12 requirement [S77][S78]. In the Simulator, use a Debug launch argument, `DEBBIE_QR_PAYLOAD`, or the paste path [S63].

### F1. Architecture and module boundaries

**F1.1 Local package or frameworks**
- Apple recommends organizing app code into **local Swift packages** in the same repository, added to the app target as library products [S6].
- The manifest API in the local toolchain offers only `library`, `executable` and `plugin` products, and only `target`, `executableTarget`, `testTarget`, `binaryTarget`, `systemLibrary` and `plugin` targets. There is no app or app-extension product, so the app and the NSE must live in an Xcode project (verified in the local toolchain) [S58].
- Reasoning: declare products without `type:` and never as `.dynamic`. Static linking means the NSE pays only for the modules it imports, which matters under its 24 MB cap [S19]. Check with `otool -L` that no `Debbie*.framework` appears inside either binary.

**F1.2 Code that switches by configuration (Debug-only code)**
- `TargetDependencyCondition` has only `.when(platforms:)` and, from tools version 6.1, `.when(traits:)`. **There is no configuration condition for dependencies.** `BuildSettingCondition.when(configuration:)` (`.debug` or `.release`) exists for Swift, C and linker settings (verified in the local toolchain) [S58][S44].
- XcodeGen's dependency options are `embed`, `link`, `codeSign`, `removeHeaders`, `weak`, `platformFilter`, `destinationFilters`, `platforms` and `copy`. None filters by configuration [S46].
- Package targets take settings only from `Package.swift`: `SwiftSetting.define` with platform, configuration or trait conditions [S58]. Reasoning: a flag set in the app's xcconfig, such as the demo-home switch, therefore can't switch code inside a package. Code that a build setting must remove belongs in the app target.
- Not documented in [S44]: how Xcode maps a configuration whose name isn't "Debug" or "Release" onto SwiftPM's `.debug`/`.release` (see Open questions).

**F1.3 State: Observation and SwiftUI** (all verified in the local SDK)
- `@Observable`, `@ObservationIgnored` and `withObservationTracking` need iOS 17. The `Observations` async sequence needs **iOS 26** [S57], which is Debbie's minimum (X18), so it needs no availability check.
- `Environment(_ objectType:)` and `.environment(_ object:)` for `Observable` types need iOS 17. The `@Entry` macro has no availability restriction [S57].
- Apple's pattern is `@State` when a view owns model state, `@Environment` for values shared widely, and `@Bindable` to make bindings [S10].
- With the old `@State`, an initial-value expression such as `@State private var model = Model()` runs every time the view struct is re-created. Xcode 27 replaces it with a macro that avoids this and back-deploys to iOS 17 [S2]. **This needs the iOS 27 SDK.** With Xcode 26.6 we keep the old behaviour, so `Model.init()` must be cheap and have no side effects (Reasoning from [S2]).
- The macro is "largely source compatible … with a few exceptions" [S2]:
  - a `@State` that has an initial value and is also assigned in an `init`: "some such cases no longer compile";
  - "The state macro disables" the synthesized private memberwise initializer that an extension of the same type can call;
  - "Composing `@State` with other property wrappers or macros is not supported";
  - generic arguments are inferred less flexibly.
- Apple's fix is to declare the property without a value and assign it in `init`. That pattern also compiles with Xcode 26.6's property-wrapper `@State` (local check [S62]). R4 turns these into rules.
- `@Entry` expands its default into a computed getter, so the default expression runs on every read of the default (local macro expansion [S62]). The iOS 27 SDK's `@Entry` "now warns of potential issues if you store default class instances or closures in the environment" [S2].

**F1.4 Swift 6 concurrency settings** (verified in the Xcode 26.6 build-setting specs [S59] and the manifest API [S58])
- `SWIFT_DEFAULT_ACTOR_ISOLATION`: `nonisolated` (the default) or `MainActor`, which adds `-default-isolation=MainActor`.
- `SWIFT_APPROACHABLE_CONCURRENCY`: Boolean, default NO. It "enables DisableOutwardActorInference, GlobalActorIsolatedTypesUsability, InferIsolatedConformances, InferSendableFromCaptures, and NonisolatedNonsendingByDefault". The spec marks this umbrella setting as applying only to Swift 4/4.2/5, along with the older features in its list (`SWIFT_UPCOMING_FEATURE_DISABLE_OUTWARD_ACTOR_ISOLATION`, `…_INFER_SENDABLE_FROM_CAPTURES`). The two Swift 6.2 features, `SWIFT_UPCOMING_FEATURE_NONISOLATED_NONSENDING_BY_DEFAULT` and `SWIFT_UPCOMING_FEATURE_INFER_ISOLATED_CONFORMANCES`, carry no such condition and default to `$(SWIFT_APPROACHABLE_CONCURRENCY)` [S59].
- SwiftPM equivalents: `.enableUpcomingFeature(_:)` is available from tools version **5.8**; `.defaultIsolation(MainActor.self)`, `.treatAllWarnings(as:)` and `.strictMemorySafety()` need tools version **6.2** (the manifest API's `@available(_PackageDescription …)` annotations) [S58]. R2's tools version 6.2 is needed for `.defaultIsolation`, not for the upcoming features.
- Apple: "The Approachable Concurrency setting enables a suite of upcoming features … We recommend that all projects adopt this setting." Separately, it recommends MainActor default isolation "for Swift modules that are primarily interacting with the UI, such as your main app module" [S8]. So the features are for every module; MainActor isolation is only for UI modules.
- `@concurrent` "tells Swift to run the function in the background"; "An @concurrent function will always switch off of an actor to run. If you want the function to stay on whatever actor it was called on, you can use the nonisolated keyword" [S8][S9]. The build-setting spec describes `NonisolatedNonsendingByDefault` as: "Runs nonisolated async functions on the caller's actor by default unless the function is explicitly marked `@concurrent`" [S59].
- The umbrella's three older features (`DisableOutwardActorInference`, `GlobalActorIsolatedTypesUsability`, `InferSendableFromCaptures`) default through `SWIFT_UPCOMING_FEATURE_6_0`, with the same Swift 4/4.2/5 condition as the umbrella [S59]. Reasoning from those conditions: in Swift 6 mode they are already on, so adopting Approachable Concurrency means turning on the two Swift 6.2 features.
- Local compile checks, with Swift 6.3.3 and an iOS 17 target [S62]. During the review, (a)–(c) were re-run at an **iOS 26.0** target with both upcoming features on, with the same results. A nonisolated Core module with an `actor`, a typed-throws protocol and an `@concurrent` CryptoKit function also compiles with both features:
  - (a) An NSE subclass built with `-default-isolation MainActor` fails with three errors: "main actor-isolated instance method 'didReceive(_:withContentHandler:)' has different actor isolation from nonisolated overridden declaration", plus the same for `serviceExtensionTimeWillExpire()` and `init()`. The base class has no isolation or Sendable annotations [S50].
  - (b) The same file compiles once declared `nonisolated final class`.
  - (c) It also compiles with the default `nonisolated` isolation.
  - (d) An `@Observable` model in a MainActor-default module that calls `HKAnchoredObjectQueryDescriptor.result(for:)` compiles.
  - (e) A two-module skeleton compiles: a nonisolated Core with `Sendable` structs, an `actor` and a protocol using typed throws `throws(TransportError)`, plus a MainActor UI module with an `@Entry` existential environment value, an `@Observable` model and `@State`.
- Sendability in the SDK: `HKHealthStore` and `HKQueryAnchor` are `NS_SWIFT_SENDABLE`, and the HealthKit query descriptors are `Sendable` structs [S52]. `DataScannerViewController` is `@MainActor` [S53]. The NSE's content handler block isn't marked Sendable [S50].

**F1.5 Dependency injection and errors**
- Protocols live in Core and are injected through `@Entry` environment values. Typed throws at module boundaries compile and let `catch` see the concrete error type without casting (verified in [S62]).
- Swift's own guidance (SE-0413): the untyped `throws` "remains the better default error-handling mechanism for most Swift code". Typed throws fits "code that stays within a module or package where you always want to handle the error", generic code that only passes errors through, and constrained environments [S74]. Every Debbie module boundary is inside one local package, and every error is handled (mapped to a screen state), so the first case applies. That is the limit R5 sets.
- Reasoning: each feature module maps its domain errors to a small user-facing state enum. That gives every error a defined recovery screen, as brief §5.2 requires ("errors with a way to recover").

### F3. Sharing Keychain items between the app and the NSE

- An app's keychain access groups are, in order: its `keychain-access-groups` entries, then its application identifier (team ID plus bundle ID), then its app groups. The first keychain group is the default. App group names can also serve as keychain groups [S11].
- Xcode quietly prefixes keychain group names with `$(AppIdentifierPrefix)` [S12]. App group IDs (`group.<name>`) must be registered on the developer website [S13]. The keychain entitlement comes from the Keychain Sharing capability [S14].
- Reasoning: Xcode's cached capability list includes App Groups but has no Keychain Sharing entry to enable on an App ID [S60]. So keychain sharing needs no identifier registration, while an App Group does [S13].
- Writing to a group the app doesn't belong to fails with `errSecMissingEntitlement` (−34018). Querying such a group returns `errSecItemNotFound` [S11][S51]. Other codes: −25299 duplicate, −25300 not found, −25308 interaction not allowed [S51].
- `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`: readable once the device has been unlocked after a restart, "recommended for items that need to be accessible by background applications", and never migrates to a new device through a backup [S51]. The `Always` classes have been deprecated since iOS 12 [S51].
- **Simulator.** For Simulator builds, Xcode links the entitlements into the binary (`LD_ENTITLEMENTS_SECTION` adds `-sectcreate __TEXT __entitlements`) (verified locally) [S59]. Apple DTS confirmed (Sep 2016) that iOS 10 and later simulators honour entitlements, and that keychain calls fail when the entitlements lack `application-identifier` [S15]. Logic tests run in `xctest`, which has no entitlements, so keychain tests must be **app-hosted** [S15].
- I tried a hand-built, ad-hoc-signed simulator app with a team-less group string to test whether a team-less group works. It was **inconclusive**: SpringBoard refused the launch and `simctl spawn` gave "Security policy issue", and the test app was removed afterwards. Whether an Xcode build with no team can use a team-less group string remains open.
- **Reinstall.** That items survive app deletion is an undocumented "implementation detail" (DTS, Dec 2017). It's the observed behaviour since a 10.3 beta change was rolled back, so code should "act reasonably if that behaviour changes" [S16].

### F4. Notification Service Extension

- It runs only for remote notifications with an `alert` (title, subtitle or body) and `mutable-content: 1`, and only if alerts are enabled. Silent notifications and those that only play a sound or badge are never passed to it [S17][S18].
- It has "only about 30 seconds". Then `serviceExtensionTimeWillExpire()` is called and you "must return whatever you can". If the handler is never called, the original content is shown [S17]. Its `Info.plist` sets `NSExtensionPointIdentifier = com.apple.usernotifications.service` and the principal class [S18].
- **Memory:** "limited to 24 MB", which is "the total memory allowed, which includes your code, any linked libraries/frameworks, and in-process allocation". Going over is a jetsam kill that appears in the jetsam logs, not as a crash (Apple engineer, Nov 2025) [S19].
- **Payload:** at most 4 KB (4096 bytes). `interruption-level` takes `passive`, `active`, `time-sensitive` or `critical`; `relevance-score` is 0–1; `thread-id` maps to `threadIdentifier` [S21]. `apns-collapse-id` merges notifications and must be at most 64 bytes. `apns-push-type` is recommended on iOS. `apns-priority` 10 sends at once; 5 lets delivery be batched or throttled for power [S20].
- `UNMutableNotificationContent` has `title`, `body` and `threadIdentifier`, `targetContentIdentifier` (iOS 13), `interruptionLevel` and `relevanceScore` (iOS 15), and `filterCriteria` (iOS 16) (verified in the local SDK) [S50].
- **Time Sensitive** is a public capability with the Boolean entitlement `com.apple.developer.usernotifications.time-sensitive` (in Xcode's cached capability list) [S60]. That entry's `supportedProductTypes` are only `com.apple.product-type.application` and `com.apple.product-type.watchkit2-extension` [S60]. An iOS app extension such as the NSE isn't listed, so the capability belongs on the app's App ID only. Such notifications break through Notification Summary and Focus, and people can turn this off [S23]. Apple's guidance: enable the capability, and use it only when the notification needs immediate attention. Critical alerts still need an approved entitlement [S24].
- **Filtering** (`com.apple.developer.usernotifications.filtering`) needs an application to Apple. It lets an NSE suppress a notification [S22], and it isn't public in Xcode's capability list [S60].
- CryptoKit has no APIs marked unavailable to extensions. `Curve25519`, `ChaChaPoly`, `HMAC` and HKDF-derived keys are all available from iOS 13 (verified in the local SDK) [S56].
- Extensions share their app's Local Network state, and extensions assumed to run in the background are denied while it's undetermined [S35]. Reasoning: the NSE must never use the LAN.
- **Testing.** `simctl push` accepts alert payloads of up to 4096 bytes [S63], but NSEs don't run for simulated pushes: "The `mutable-content` key is not honored" [S25]. From Xcode 14, the Simulator (iOS 16 or later, macOS 13, Apple silicon or T2) can receive real **sandbox** APNs pushes, which do support NSEs [S26].
  - Sending any real push, to the Simulator or a device, needs provider credentials. "APNs validates the request using either the provided authentication token or your server's certificate" [S20]. The token is signed with "an APNs authentication token signing key" requested from the developer account [S72].
  - `asc.env` holds only an App Store Connect API key, and Layer 1 puts "the team's APNs key" on the relay side ("SNS → APNs") [S64]. So even once `asc.env` exists, the iOS track can't send a push itself. The end-to-end NSE test is the relay team's push test (Layer 1 build step 0b) [S64], as note 11b R13 also says.
  - What the iOS track can test locally is the real NSE class: `UNNotificationRequest` has the public initializer `requestWithIdentifier:content:trigger:` (trigger nullable), and `UNNotificationServiceExtension`'s `init` and `didReceiveNotificationRequest:withContentHandler:` are public [S50]. A test can therefore build a request and call the extension directly (typechecked locally [S62]; R14).

### F5. HealthKit heart rate

- **Setup.** Call `HKHealthStore.isHealthDataAvailable()` before anything else, and add the HealthKit capability, which sets the HealthKit entitlements [S27]. `NSHealthShareUsageDescription` is the reading message and `NSHealthUpdateUsageDescription` the writing message [S28]. Xcode 26.6 can generate both, plus `NSCameraUsageDescription` and `NSLocalNetworkUsageDescription`, from `INFOPLIST_KEY_*` build settings. It can't generate `NSBonjourServices` or `NSAppTransportSecurity` (verified in the local spec) [S59].
- **Authorization.** An app can't tell whether reading was denied: denied reads return only the samples the app saved itself [S28]. The authorization sheet "doesn't display" in a Guest User session [S28]. **iOS 27** adds a second screen where the person grants limited or full history [S2][S28]. The matching `earliestAuthorizedSampleDate(for:)` is iOS 27.0 only [S33] and isn't in the local 26.5 SDK (grep found nothing). **It needs the iOS 27 SDK.**
- **Reading "everything since the last check".** `HKAnchoredObjectQueryDescriptor` (iOS 15.4) has `result(for:)`, which returns `addedSamples`, `deletedObjects` and `newAnchor`, and `results(for:)` for a long-running stream (verified) [S52]. "If you pass nil as the anchor parameter, the query reads all matching data", so read in batches with `limit` [S30]. `HKQueryAnchor` adopts `NSSecureCoding` [S52].
- **Units.** The heart-rate identifier's canonical unit is `count/s` (header comment), so convert explicitly to beats per minute with `HKUnit.count().unitDivided(by: .minute())`, which compiles [S52][S62].
- **Locked phone.** "The device encrypts the HealthKit store when the user locks the device", so background reads may fail, though writes are cached [S29]. The error is `HKErrorDatabaseInaccessible`, "Protected health data is inaccessible because the device is locked" [S52]. UIKit's `isProtectedDataAvailable` and `protectedDataDidBecomeAvailableNotification` signal an unlock (verified) [S61].
- **Background delivery.** It needs the `com.apple.developer.healthkit.background-delivery` entitlement from iOS 15, or `enableBackgroundDelivery` fails with `errorAuthorizationDenied` [S31][S32]. "HealthKit wakes your app whenever a process saves or deletes samples of the specified type", "at most once per time period" set by the frequency. Some types have an hourly maximum: on iOS, step count is the example given [S31]. **Heart rate's iOS limit isn't documented.** On watchOS, only the listed event types can be immediate [S31]. Nothing in [S31] limits waking to a locked phone, so it also covers an unlocked phone with Debbie in the background. While the phone is locked, HealthKit caches writes and "saves it to the encrypted store as soon as the user unlocks the phone" [S29]. Whether that save at unlock wakes observers isn't documented (Open question 9).
- Set up observer queries in `application(_:didFinishLaunchingWithOptions:)` and always call the completion handler. After three failures to respond, HealthKit stops background delivery. "Background server queries aren't supported on the Simulator" [S31].
- **Simulator.** The Simulator has a Health app and HealthKit store that apps can read; Apple's sample-account guide shows this for clinical records [S34]. `simctl privacy` has no Health service (nor camera, local network or notifications), so HealthKit authorization can't be granted from a script (verified locally) [S63].

### F6. Local network, Bonjour and ATS

**Local network privacy** (TN3179, revised 2026-10-06) [S35]
- Definition: "A local network is an IP network associated with a broadcast-capable network interface. Such interfaces include Wi-Fi and Ethernet, but not cellular (WWAN) or VPN. A local network address is any address on a local network. Traffic to a local network address goes directly; it's not forwarded by a router."
- The alert appears on the first local-network operation, such as an outgoing TCP connection to a LAN address, resolving `.local`, or any Bonjour register, browse or resolve. "There's no API to explicitly bring up the local network alert" and "no general API that returns whether the current process has local network access."
- "It may deny the operation immediately, before the user has responded", so use Network framework or URLSession with `waitsForConnectivity`, or add retries.
- Denied shows up as `NWBrowser` in `.waiting(.dns(kDNSServiceErr_PolicyDenied))` (−65570), or as `NWConnection` in `.waiting` with `currentPath?.unsatisfiedReason == .localNetworkDenied`. When the user later allows access, NWConnection retries automatically.
- In the background with the state undetermined, operations are denied without an alert, and the decision isn't recorded.
- **"The simulator doesn't support local network privacy. Test … on a real device."** Reset by deleting the app. iOS 18 had a state-sync bug, fixed in 18.6.
- Put `NSLocalNetworkUsageDescription` and `NSBonjourServices` in the **app's** Info.plist, not the extension's. The multicast entitlement is needed only for arbitrary or all service types, not for one named type.

**Supporting facts**
- Both Info.plist keys date from iOS 14. `NSBonjourServices` lists types such as `_ipp._tcp` [S36][S37].
- Network framework (verified in the local SDK) [S55]: `NWBrowser` and `.bonjour(type:domain:)` need iOS 13; `NWConnection` and `NWPathMonitor` iOS 12; `NWPath.UnsatisfiedReason.localNetworkDenied` iOS 14.2. The Swift-concurrency types `NetworkBrowser`, `NetworkConnection`, `NetworkListener` and `Bonjour` need **iOS 26**. `kDNSServiceErr_PolicyDenied = -65570` is in `dns_sd.h`.
- `URLSessionConfiguration.waitsForConnectivity` (iOS 11) and `timeoutIntervalForResource` are verified in the local SDK [S61]. `timeoutIntervalForRequest` is an idle timer, "reset whenever new data arrives" (default 60 s). `timeoutIntervalForResource` "starts when the request is initiated" and caps the whole request (default 7 days). `waitsForConnectivity` is "relevant only during the establishment of a connection" [S61].
- `getifaddrs` with `ifa_netmask`, and the flags `IFF_UP`, `IFF_BROADCAST`, `IFF_LOOPBACK` and `IFF_POINTOPOINT`, are in the iOS SDK (`ifaddrs.h`, `net/if.h`). An interface scan using them typechecks for iOS 26 [S55][S62].

**Bonjour discovery and resolution** (APIs verified in the local SDK [S55])
- Layer 1 fixes the service: "The coordinator's bridge advertises its network side by mDNS (Bonjour) as `_debbie._tcp` on port 7480, with the first 8 characters of the hub's public key (base64url) in its TXT record, so phones and laptops can tell homes apart" [S64]. CONTRACTS.md §4 proposes `hub` as the TXT key name.
- `NWBrowser.Descriptor.bonjourWithTXTRecord(type:domain:)` (iOS 13) delivers each result's TXT record as `Result.metadata == .bonjour(NWTXTRecord)`. `NWTXTRecord` has `subscript(key:) -> String?` and `dictionary`. In iOS 26, `NetworkBrowser(for: .bonjour(_:domain:includeTxtRecord:))` gives the same through `Bonjour.Endpoint.txtRecord`, and `TXTRecordDecoder` (iOS 18) decodes a record into a `Decodable`.
- A browse result is a service (`NWEndpoint.service(name:type:domain:interface:)`), not an address. Apple DTS: a browser "does not return address information (local DNS name, IP address list, port)", and "Network framework does not have an API that does the Bonjour *resolve* operation without also connecting". "Building a URL from a Bonjour service is one of the few cases" where you need a resolve [S69].
- Two ways to resolve. One is a throwaway `NWConnection` to the service, reading the address it used; DTS says this "will certainly work", but "saves code complexity at the expense of runtime and network efficiency". The other is `DNSServiceResolve` from `<dns_sd.h>`, which "is not deprecated" [S69][S70]. After `.ready`, `NWConnection.currentPath?.remoteEndpoint` is a `.hostPort(host:port:)` [S55]. URLSession takes URLs, so it can't use a service endpoint directly.
- mDNS timing: a querier "SHOULD also delay the first query of the series by a randomly chosen amount in the range 20-120 ms". "The interval between the first two queries MUST be at least one second", and later intervals at least double. Responders delay shared answers by 20–120 ms [S71]. A browse therefore queries at about 0.1, 1.1, 3.1 and 7.1 s.
- `NWPathMonitor` is an `AsyncSequence` of `NWPath` from iOS 17 [S55].

**App Transport Security**
- ATS applies to connections made with the URL Loading System [S40].
- "In iOS 17 … ATS no longer allows connections to IP addresses by default." `NSAllowsLocalNetworking` "controls whether ATS allows your app to connect to unqualified domains, `.local` domains, and IP addresses using IPv4 or IPv6" [S38]. Apple recommends setting it "as a declaration of intent" even where it isn't strictly needed [S38].
- `NSExceptionDomains` **can** list an IPv4 or IPv6 address or a CIDR range from iOS 17, iPadOS 17 and macOS 14 (iOS 9–16 couldn't). An IP exception doesn't apply when the same host is reached by DNS name, or the other way round [S39].
- Exceptions that need App Review justification include `NSAllowsArbitraryLoads` and `NSExceptionAllowsInsecureHTTPLoads`. `NSAllowsLocalNetworking` isn't on that list [S41].
- This confirms the Layer 1 doc: "from iOS 17, App Transport Security blocks connections to IP addresses otherwise" [S64].

### F7. QR scanning

- `DataScannerViewController` needs iOS 16 and is `@MainActor`. It has the class properties `isSupported` and `isAvailable`, the data types `.barcode(symbologies: [VNBarcodeSymbology])` and `.text`, and the init options `qualityLevel`, `recognizesMultipleItems`, `isHighFrameRateTrackingEnabled`, `isPinchToZoomEnabled`, `isGuidanceEnabled` and `isHighlightingEnabled`. It has `startScanning() throws`, `recognizedItems` as an `AsyncStream<[RecognizedItem]>`, and `ScanningUnavailable.unsupported` and `.cameraRestricted` (verified in the local SDK) [S53].
- `isSupported` requires "the A12 Bionic chip and later". `isAvailable` is false if camera access is denied or restricted. `dataScanner(_:becameUnavailableWithError:)` fires, for example, when the user taps Don't Allow [S43]. You need `NSCameraUsageDescription` and the person's consent [S42].
- AVFoundation alternative: `AVMetadataObjectTypeQRCode` (iOS 7) with `AVCaptureMetadataOutput`. `setMetadataObjectTypes:` throws `NSInvalidArgumentException` for types not in `availableMetadataObjectTypes`, so add the output to a configured session first, and deliver its delegate calls on a serial queue. `AVCaptureDevice.authorizationStatusForMediaType:` and `requestAccessForMediaType:` handle permission (verified in the local SDK) [S54].
- **Simulator.** There's no camera. `simctl launch <device> <bundle> [argv…]` passes launch arguments, `SIMCTL_CHILD_*` passes environment variables, and `simctl pbcopy` fills the device pasteboard (verified locally) [S63].
- Reasoning on size: the QR JSON from [S64] (`v`, IPv4 `addrs`, a 43-character base64url `hub_pub`, a 22-character `secret`, `exp`) is roughly 200 bytes for one or two addresses, well inside a medium-density QR code.

## What changed in the current iOS release

- **HealthKit (iOS 27):** people can grant limited or full history. `earliestAuthorizedSampleDate(for:)` reports the limit [S2][S33]. **Needs the iOS 27 SDK.** Debbie reads only recent data (R16), so it's unaffected. Old data before a limited window must be shown as "unknown", never as "no data" [S33].
- **SwiftUI (Xcode 27):** the `@State` macro stops re-evaluating initial values; it back-deploys to iOS 17 [S2]. **Needs Xcode 27 / iOS 27 SDK.** Until then, keep `init` side-effect free (R4).
- **UIKit (27 SDK):** apps built with the latest SDK must use the scene-based life cycle, and apps built with the 27.0 SDK must include a launch screen [S2]. SwiftUI's `App` is scene-based. The launch screen is the design notes' job. This takes effect once we move to the 27 SDK.
- **Notifications (iOS 27):** only a fix ("Critical alerts are automatically turned on…" fixed) [S2]. The NSE API is unchanged (the local 26.5 headers match the current docs [S50][S18]).
- **Network Security (iOS 27):** stricter TLS for *system* processes only (MDM, installs, updates), not for apps [S2]. ATS rules for apps are unchanged.
- **Local network privacy:** TN3179's latest revision (2026-10-06) concerns only the reset buttons in macOS 27.2. Nothing changed for iOS [S35].
- **Keychain, VisionKit, AVFoundation QR, Network framework:** nothing relevant in the iOS 27 release notes [S2].
- **Tools:** Xcode 27 has Swift 6.4 and requires macOS Tahoe 26.6 or later, which this Mac can't run [S4]. XcodeGen's next release adds an `xcode27_0` project format and a fix for Xcode 27.2 project conversion [S45]. That matters only if a Layer 4 contributor opens the project in Xcode 27.2.

## Open questions / risks

1. **Team-less Simulator keychain groups.** Does a team-less Simulator build accept `kSecAttrAccessGroup = <prefix-less>.shared`? My hand-built test was inconclusive (launch refused). R10 settles it in the first Phase 4 test, and has a fallback.
2. **Configuration mapping for packages.** How Xcode maps a configuration not named "Debug" or "Release" onto SwiftPM's `.debug`/`.release` isn't documented [S44]. Mitigation: keep exactly those two names (R6) and the `nm` check.
3. **Time-sensitive level after the NSE.** Does a notification whose level the NSE lowered keep the right behaviour, and does the NSE's App ID also need the Time Sensitive capability? Test on a device with Focus on. If needed, enable it on `BUNDLE_ID.<suffix>`, as brief §3 allows.
4. **Heart-rate background frequency on iOS** isn't documented [S31]. R17 assumes it's sparse.
5. **NSE memory headroom.** CryptoKit plus Foundation should be far below 24 MB, but measure on a device: use `log stream` for jetsam events while sending 10 pushes [S19].
6. **Bonjour service type.** `_debbie-hub._tcp` needs the bridge team's agreement (CONTRACTS.md), and the 15-character rule should be checked against the DNS-SD specification before freezing.
7. **XcodeGen and Xcode 27.2.** A contributor on Xcode 27.2 may hit the project-conversion bug that is fixed only in XcodeGen's unreleased version [S45]. Mitigation: they open the committed project, and we regenerate with the next XcodeGen release when it ships.
8. **iOS 27 limited-history authorization** can't be detected with the 26.5 SDK [S33]. Debbie only reads recent data (R16), so the impact is low.
