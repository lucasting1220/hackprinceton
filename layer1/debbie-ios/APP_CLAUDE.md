## Process
- Research before deciding. Every CRAFT.md rule cites a source (HIG, Apple docs, WWDC, Apple Design Award and App Store editorial first) or written reasoning. Taste is not a source. Never copy any app's identity, assets, layouts or copy.
- Commit to the LOCAL git repo at every working checkpoint. Never push, never add remotes, never open PRs or issues.
- Never wait for a human. Owner decisions get the most conservative option that keeps work moving, listed under "Decisions to confirm". A refused or approval-gated tool call goes under Blockers; carry on with the tools that work. Never change Claude Code's permission settings.
- Nothing is done without evidence: a build log, a passing test, a screenshot you opened and looked at, a screen recording whose frames you inspected, or an App Store Connect response.
- Independent review where the brief asks: a fresh subagent with no stake, told to find problems. If that's impossible, do a separate self-review pass and say so in the report.
- Phases 0–7 each end with a gate (brief §8). Don't start the next phase until it passes, or record why it can't and what you did instead.

## Design
- Mint is the signature colour and MUST read as mint. Use companion tokens for text and behind text. Never shift mint toward teal, sage or forest to pass contrast. The palette is calm and simple, with semantic tokens for light, dark and Increase Contrast. It shows real urgency (a possible fall) without breaking the calm, works for colour-blind users, and every text and icon pairing has its ratio measured and recorded in CRAFT.md.
- Featured-app craft: spring-based, interruptible motion carrying gesture velocity; purposeful, consistent haptics matched to meaning; fluid transitions with continuity. **Every animation and haptic comes from CRAFT.md tokens** (named springs, transitions, haptic events). A test or lint MUST fail on raw animation curves or haptic calls outside the design-system code.
- Simplicity: CRAFT.md defines, from research, what simplicity means for each screen and how to check it. Every screen has one clear job.
- Custom-design every asset: the logo and wordmark; the app icon in every variant current iOS uses (generated from scripts where the format is documented, and proven to compile with `actool`; otherwise ship default/dark/tinted in an asset catalog, record the gap in DECISIONS and list it to confirm); a complete icon set; buttons and controls; empty states; the launch screen; any illustrations research calls for. No stock or downloaded art, icon packs, third-party UI kits or placeholders in any uploaded build. Each asset has an editable vector source in the repo and an export script.
- **SF Symbols and every other system-provided glyph are stock**: never in the app's own interface (tab bars, toolbars, navigation, buttons, lists, empty states, notification content, widgets). **Every stylable control** (buttons, toggles, segmented controls, tab and navigation bars, back buttons, sheet headers, progress indicators, text fields) uses Debbie's own component, never the system default look. Where Apple's design language would mean a system-drawn control unchanged, build a custom component that meets the same guidance, and record it in DECISIONS.
- Exempt only: surfaces the system draws that can't be restyled (permission prompts, share sheet, keyboard, system alerts). System typefaces are allowed; any other typeface needs a bundling licence recorded in DECISIONS.
- Accessibility is a hard requirement: VoiceOver, Dynamic Type to the largest accessibility sizes, Reduce Motion, Increase Contrast, colour never the only signal. The thresholds are in CRAFT.md.

## Engineering
- Build, test and ship entirely from the command line: no Xcode GUI, no GUI dialog, no typed password.
- Final build: no warnings from Debbie's own code or project settings, and test suites green. A warning from a prebuilt third-party binary that can't be fixed without rebuilding it is recorded word for word in DECISIONS and doesn't fail a gate.
- No third-party dependency without a DECISIONS entry (purpose, alternatives, maintenance, licence). The live viewer needs a maintained community build of Google's WebRTC.
- No analytics, tracking, advertising or third-party crash reporting.
- Mocks, debug menus, fixtures and test hooks stay out of Release builds. **The one exception is the on-device demo home (brief §6).**
- The project is relocatable: no absolute paths in the project, the scripts or the fastlane setup.

## Contracts, routes, mock home, demo home (brief §6)
- Follow the Layer 1 doc's "Phone ↔ hub messages" exactly (QR, pairing request and proof, keys, 4-digit code, envelope, freshness, credentials), even where the laptop track differs; list each difference in the report. Never invent cryptography. For gaps, match `layer-1` work where it exists (mark ADOPTED with the commit hash) unless that breaks a doc guarantee (the relay sees only ciphertext and routing data; heart rate never goes through the relay; the device credential never crosses the LAN). Otherwise PROPOSE, with example payloads. Keep the phone-to-hub part of CONTRACTS.md self-contained, ready to copy to `layer1/contracts/phone-hub.md`. Define requests and replies (`ask`, `check_now`) too.
- Test vectors come from the Swift tests and are verified with Node's built-in `crypto` in the test lane, then published in CONTRACTS.md.
- Routes are chosen at run time. For caregivers the relay is the main path; the LAN gateway is used on home Wi-Fi when it answers. If it fails, fall back to the relay with no prompt and no re-pairing. Pairing, adding a laptop over Wi-Fi, and heart rate need the LAN gateway; rediscover it by Bonjour (`_debbie._tcp`), confirm with a request encrypted with the phone's own key, and update the stored addresses. Configuration may only override the choice (mock home, force LAN, force relay). Measure simulated reconnection against the 30 s target and record it in PROGRESS.
- **Mock home:** a separate Node server in this repo, outside the app target, **127.0.0.1 only**. It plays the bridge, LAN gateway and relay over real HTTP, advertises by Bonjour like the real bridge, and has controls for alerts, updates, late delivery, status changes, hub offline, monitoring degraded, a removed phone, the LAN gateway becoming unreachable or moving, and every live-view state (requesting, denied, ready, connecting, playing, ended by time limit, ended by you, ended by the resident, failed). Debug builds may reach the mock relay over plain HTTP on 127.0.0.1. Release builds require HTTPS for the relay and allow plain HTTP only to local-network addresses; a test checks the Release settings. The Simulator has no camera: Debug builds can be fed a QR payload.
- **On-device demo home:** TestFlight builds SHOULD include one. It is clearly labelled, chosen explicitly from onboarding, runs entirely on the phone with no network and marked demo data, is never mixed with a real pairing, can be removed with one build setting, reaches every §5.1 screen and fires every named haptic event. List it under "Decisions to confirm".

## Security, accounts, limits
- Never commit, print or log secrets (ASC keys, certificates, profiles, passwords, device credentials, the home key). Check credentials for presence only; never open, copy or print the `.p8`. Build, fastlane and test-result logs go in a gitignored folder. **Before every commit**, check the staged changes contain none of the `ASC_KEY_ID`, `ASC_ISSUER_ID` or `ASC_KEY_PATH` values or any `.p8` content (`.githooks/pre-commit`). `BUNDLE_ID`, `APPLE_TEAM_ID` and `DEMO_IOS_VERSION` aren't secrets: they go in a generated, gitignored `Config/Local.xcconfig` (D-002). `.gitignore` covers at least `*.p8 *.p12 *.cer *.mobileprovision *.ipa *.dSYM.zip fastlane/report.xml` and the build and log folders.
- Credentials come only from `~/.config/debbie-ios/asc.env` (`ASC_KEY_ID`, `ASC_ISSUER_ID`, `ASC_KEY_PATH`, `APPLE_TEAM_ID`, `BUNDLE_ID`, `DEMO_IOS_VERSION`), read at run time, plus signing items created under these rules. If the file, a credential or the key is missing or invalid, NEVER use other credentials and NEVER search the disk or the keychain for any. Build, test and archive locally, keep the pipeline ready, record the blocker. `gh` may read GitHub, never write.
- fastlane authenticates with that API key only, non-interactively (stdin closed). Never Apple ID or 2FA.
- Identifiers: register only `BUNDLE_ID`, `BUNDLE_ID.<suffix>` extensions, and the app group and Keychain group matching `BUNDLE_ID`. On those you MAY enable the capabilities the uploaded app uses and create profiles: list each capability in PROGRESS before enabling it, and never disable or remove one. Touch nothing else. If `BUNDLE_ID` or `APPLE_TEAM_ID` is missing, register nothing.
- Signing: never revoke, delete, regenerate or modify any existing certificate, profile, identifier, key or app. Never change the default keychain or remove anything from the search list. An added keychain is appended to the search list and recorded with how to undo it. At the certificate limit: stop and record it.
- TestFlight: MAY upload for internal testing and add builds to an existing internal group. If none exists, MAY create one with only existing App Store Connect users. MUST NOT invite anyone, create external groups, submit for App Review or Beta App Review, or change other settings. Export compliance: set only the Info.plist answer; never answer through the API, fastlane or any other route.
- No AWS or other cloud account, no deploying, no spending money, no `sudo`. Write only in this folder, except tool caches, user-level installs (Homebrew; gems via bundler) and allowed signing items. Record every install and signing item, with how to undo it, in the report. The team repo is read-only.

## Delivery (brief §7)
fastlane pinned with Gemfile and bundler; lanes for test, build and TestFlight, unattended and non-interactive. Preflight: presence of every value, a read-only call proving the key works, its role, the app record, and an internal group with automatic distribution and ≥ 1 tester (record the name and count only). Signing proven in Phase 0 by a throwaway signed archive and export (no upload), in the background, with a time limit. Minimum iOS ≤ `DEMO_IOS_VERSION`, the most inclusive that still meets CRAFT.md. Build number above the latest TestFlight build. Push environment set and reported at token registration. Archive and upload in the background, logs in the gitignored folder, never waiting on processing. Validate each archive (usage strings, privacy manifest, icons, versions). At most about one upload an hour, plus the final one. INVALID, or two failures for the same reason: stop and fix. The first upload (Phase 4) is a minimal shell: app icon, launch screen, one screen with logo and wordmark, no system-default controls, with the push and Time Sensitive entitlements and the extension with its shared Keychain group. Every upload goes to the internal group with "What to Test" notes, recorded in PROGRESS.
