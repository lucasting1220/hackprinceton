# Plan: Layer 4 step 1, part 1: rules and template alerts

Branch: `l4/rules-upper-tier`. Scope: only `layer4/`. Contract files touched: none.

## What this step builds

The upper tier's fixed rules, run on hand-written test signals, and the template alert each rule produces. Nothing is sent anywhere and nothing is written to the event log yet.

Part 2 (a later branch) adds event log writing, once an event log contract is on `main`. Step 3 sends alerts to Layer 1, once an alert contract exists.

## Decisions already made (by the Layer 4 owner, Nov 14)

- `kind` is one of `fall`, `help`, `heart_rate`, `monitoring`. `severity` is always `urgent`; nothing below a threshold produces an alert.
- `title` is a short fixed name; `body` is the Layer 4 doc's template line with the time filled in. The step 5 rewrite will replace only the body.
- `{time}` in the body is the worker laptop's local time, for example `3:12 AM`. `detected_at` stays UTC.
- Thresholds are named settings with the doc's proposed values, never hardcoded in the rules (CLAUDE.md section 2, item 2).

## Signals

All times are timezone-aware datetimes. A naive datetime raises `ValueError`.

| Signal | Fields | Validation |
|---|---|---|
| `FallSignal` | `confidence: float`, `detected_at` | confidence in [0, 1] |
| `HelpSignal` | `is_call_for_help: bool`, `detected_at` | none beyond time |
| `HeartRateSignal` | `bpm: int`, `measured_at` | bpm > 0 |
| `MonitoringSignal` | `what_stopped: str`, `stopped_at`, `checked_at` | `what_stopped` not empty; `checked_at` not before `stopped_at` |

Current activity (walking, sitting, lying down, not in view) is not part of this step: no rule reads it, and CLAUDE.md:258 bans unused code. It arrives with live status in step 6 (review correction, Section 2).

## Rules (one signal at a time, no combining)

| Signal | Urgent when | Setting (proposed value) |
|---|---|---|
| Fall | `confidence >= FALL_CONFIDENCE_MIN` | 0.8 |
| Help | `is_call_for_help` is true | none |
| Heart rate | `bpm > HEART_RATE_HIGH_BPM` or `bpm < HEART_RATE_LOW_BPM` | 130, 40 |
| Monitoring | `checked_at - stopped_at > MONITORING_STOPPED_AFTER` | 30 seconds |

"At or above" and "more than" follow the Layer 4 doc's wording exactly.

## Template alerts

| kind | title | body |
|---|---|---|
| `fall` | Possible fall | Possible fall detected at {time} |
| `help` | Call for help | Call for help heard at {time} |
| `heart_rate` | Heart rate alert | Heart rate of {bpm} recorded at {time} on {date} (D5) |
| `monitoring` | Monitoring degraded | Monitoring is degraded: {what_stopped} |

- `alert_id`: a new UUID4 string. `update`: `False`. `severity`: `urgent`.
- `detected_at`: the signal's `detected_at`; for heart rate, the reading's `measured_at` (the risk table asks that the alert state the reading's time); for monitoring, `checked_at`.
- `{time}` is formatted without `strftime("%-I")`, which fails on Windows: hour `h % 12 or 12`, two-digit minutes, `AM`/`PM`. The formatter takes an optional time zone so tests are deterministic; `None` means the laptop's local zone.

## Tests (each would fail without the behaviour it checks)

- Every rule at, just below and just above each boundary: 0.79 / 0.8, 130 / 131, 40 / 39, 30 s / 31 s.
- Help true and false.
- Custom `RuleThresholds` changes the outcome (proves the rules read settings, not literals).
- Each kind's exact title and body; severity `urgent`; `update` false; two alerts get different IDs.
- Time formatting: midnight `12:00 AM`, noon `12:00 PM`, `03:12Z` in UTC−5 is `10:12 PM`.
- Validation: confidence 1.2, bpm 0, naive datetime, empty `what_stopped`, `checked_at` before `stopped_at` each raise `ValueError`.

## Section 1: Architecture

**Two shapes.** Shape 1 (the plan): one entry point `rules.decide(signal, thresholds) -> Alert | None` that matches on the signal type, with templates in `alerts.py`. Shape 2 (alternative):

```
class RuleChecker:
    def __init__(self, thresholds: RuleThresholds) -> None: ...   # not implemented
    def check_fall(self, s: FallSignal) -> Alert | None: ...       # not implemented
    def check_help(self, s: HelpSignal) -> Alert | None: ...       # not implemented
    def check_heart_rate(self, s: HeartRateSignal) -> Alert | None: ...  # not implemented
    def check_monitoring(self, s: MonitoringSignal) -> Alert | None: ... # not implemented
```

Pick: shape 1. One function hides the per-signal policy behind a single call; shape 2 exposes four methods, and every caller must pick the right one (a shallow interface).

**Red flags.** (8) hand-synced list: `AlertKind`, the template table and the rule dispatch list the same four kinds. Fix (no behaviour change, recorded as a correction): `decide` uses `match` with `typing.assert_never` in the default arm, and the template lookup is a `dict[AlertKind, ...]` checked by a test over every `AlertKind`, so a fifth kind with a missing rule or template fails `mypy` or `pytest`. No other flags.

**Failure per new path.** `decide` on a malformed signal: prevented at creation, since signals raise `ValueError`. `decide` on a stream of repeated signals: see A1.

Findings:

- A1 [INFORMATIONAL] (confidence: 8/10) layer4/plan-step1-rules.md:38 "rules.decide(signal, thresholds)" is stateless, so a fall model reporting confidence 0.9 on every frame, or a monitoring check every 2 seconds while a camera is down, yields one urgent alert per signal: a flood of push notifications. docs/layer4-care-layer.md:86-89 defines no repeat handling.
